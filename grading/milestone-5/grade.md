### Item #6a: Automated tests — integration test requirement

**What was expected**: At least 1 real integration test that exercises the application stack (e.g., using `WebApplicationFactory<T>` to send HTTP requests and verify responses).

**What was found**: [IntegrationTest.cs](api.Tests/IntegrationTest.cs) contains 2 test methods that are both marked with `Skip = "E2E coverage via Playwright against deployed API"` and have completely empty bodies — no assertions, no HTTP calls, no setup. These are placeholders, not integration tests.

**Gap**: The rubric explicitly requires "1+ integration" test. Skipped stubs with no implementation do not satisfy this. The student argues E2E Playwright coverage substitutes, but the Playwright spec is a separate rubric line item (E2E), and the rubric distinguishes integration tests from E2E tests. The student has strong unit test coverage (8 backend + 10 frontend) and a solid E2E spec, but the integration test gap costs 1 point from the testing row.

> **Note on scoring**: The rubric for this row is "1 pt" all-or-nothing for the test floor, and the integration test is explicitly listed in the requirement. However, the floor clause says "any submission with zero passing automated tests earns 0 of 2." The student has 19 passing tests across `dotnet test` (9 passed) and `npm test` (10 passed), so the floor is cleared. Given this is a single sub-bullet miss within a 1-point line item and the student has extensive passing tests otherwise, **1 point is deducted from this row**.

## 5. Code Quality Coaching (Non-Scoring)

- **Missing ownership validation on cart item updates/deletes**: [CartController.cs](api/Controllers/CartController.cs#L62-L82) — `UpdateItem` and `RemoveItem` look up cart items by ID but don't verify the item belongs to the authenticated user's cart. A logged-in user could modify another user's cart items by guessing IDs. Add a `.Where(i => i.Cart.UserId == UserId)` check.

- **Admin route not enforced on frontend**: [App.tsx](frontend/src/App.tsx#L37) — The `/admin` route only uses `RequireAuth` (checks if logged in), not an admin-specific guard. The redirect in [AdminDashboard.tsx](frontend/src/pages/AdminDashboard.tsx#L49-L52) handles this at the component level, but a dedicated `RequireAdmin` wrapper would be cleaner and more consistent.

- **No order status update UI for admin**: [AdminDashboard.tsx](frontend/src/pages/AdminDashboard.tsx) — The orders tab displays orders but has no UI to update order status. The backend endpoint `PUT /api/userorder/{orderId}/status` exists but the admin dashboard only shows a read-only status label.

- **Token expiry not handled**: [AuthProvider.tsx](frontend/src/context/AuthProvider.tsx) — The JWT has a 7-day expiry but the frontend never checks if the stored token is expired. An expired token will cause 401s with no user feedback. Consider checking `exp` claim on init and/or intercepting 401 responses to force re-login.

- **Global exception handler leaks exception details**: [GlobalExceptionHandler.cs](api/Middleware/GlobalExceptionHandler.cs#L26-L35) — `ArgumentException` and `KeyNotFoundException` handlers include `exception.Message` in the response `Detail` field. In production, this could leak internal implementation details. Consider sanitizing or omitting `Detail` in non-development environments.

- **UnitTest1.cs is a no-op**: [UnitTest1.cs](api.Tests/UnitTest1.cs) — Contains a single empty `Test1()` method with no assertions. This passes trivially but adds no value. Should be removed or replaced with a meaningful test.

- **Hardcoded admin password in seed**: [Program.cs](api/Program.cs#L104) — The admin seed password `"Password123"` is hardcoded. For a class project this is fine, but in production this should come from configuration or environment variables.
